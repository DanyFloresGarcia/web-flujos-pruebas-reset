Fase 1 · Preparación

Precondiciones que deben cumplirse antes de que un invitado pueda ejecutar un canje.

Accesos y permisos

Este flujo introduce componentes que no existían en los flujos de Configuración→Ejecución ni de Motor de Audiencia. Los accesos de AWS se diferencian por ambiente/cuenta: DEV corre en la cuenta Developer de Virginia, QA en la cuenta Developer de Ohio.

Ambiente DEV · AWS Virginia (cuenta Developer)
  • Redis: acceso de conexión y lectura, para validar claves y valores de los controles de concurrencia e idempotencia.
  • API Gateway (API de Canje): asegurar conectividad para poder invocarlo — si es público no hay problema; si es privado, definir con Plataforma cómo nos conectamos.
Ambiente QA · AWS Ohio (cuenta Developer)
  • Redis: también necesita acceso de conexión y lectura, para validar claves y valores.
  • API Gateway (API de Canje): mismo caso que DEV — asegurar la conectividad (público, o definir con Plataforma si es privado).
Configuración de la etapa y opciones
  • Etapa activa: el registro en [sch_configuracion].[cfg_etapa_segmento] debe tener la etapa asignada en CANJE, con la fecha actual dentro del rango válido de la promoción y el campo estado_etapa = 1 (Activo).
  • Configuración de la opción: debe existir el registro correspondiente parametrizado en la tabla [sch_configuracion].[cfg_opcion].
  • Proyecciones:
    • Configuración base de la proyección creada en [sch_proyeccion].[trx_proyeccion].
    • Proyección de la etapa habilitada en [sch_proyeccion].[cfg_proyeccion_etapa].
    • Stock/cantidad de opciones disponibles a contar para el sorteo parametrizadas en [sch_proyeccion].[trx_opcion_proyectada].
Participantes y acumulación de puntaje
  • Audiencia: el ID del invitado/cliente debe existir en las tablas de audiencia y participantes.
  • Migración de puntos: los puntos deben haber migrado exitosamente desde los orígenes (puntos_mixtos y puntos_mixtos_deporte) hacia la tabla de consolidación [sch_puntaje].[trx_avance], asociados al ID_ejecucion_segmento correspondiente.
  • Opciones: el invitado debe contar con opciones acumuladas en [sch_puntaje].[trx_avance] mayor o igual al valor requerido para efectuar al menos un canje.
Escalabilidad
  • Salto de opciones: el sistema debe estar configurado para monitorizar la sobrecarga de peticiones de canje y permitir la autogeneración del "salto de opciones" (habilitación dinámica de lotes adicionales de opciones) para evitar bloqueos por alta demanda.

Fase 2 · Ejecución

El servicio de canje se expone y ejecuta a través de los canales front-end, contemplando las siguientes acciones secuenciales.

1

Consulta y visualización de opciones

Front-end + BD

Al ingresar a la plataforma, el sistema consulta en tiempo real la tabla [sch_puntaje].[trx_avance] y le muestra al usuario sus opciones actuales disponibles.

2

Puntos de entrada

Front-end

El usuario inicia el flujo de canje a través de una de dos ventanas: la card del Home de Promociones (botón "Canjear") o el Detalle de la Promoción (vista expandida, botón "Canjear").

3

Validación y controles de concurrencia/idempotencia

API Promociones Web + Redis + API Gateway

Al presionar "Canjear" la petición se dirige al API Promociones Web, que obtiene y valida datos del invitado referentes al reset y luego invoca al API de Canje a través de su API Gateway — toda la ejecución del canje pasa por ahí. Antes de procesar el canje corren dos controles en Redis: concurrencia (con llave fija) e idempotencia (evita replicar el intento si el usuario reintenta el canje).

4

Procesamiento en base de datos

API Canje + BD

El sistema ejecuta obligatoriamente: INSERT en la tabla cabecera [sch_canje].[trx_canje], INSERT en la tabla detalle [sch_canje].[trx_opcion_canjeada], UPDATE en [sch_puntaje].[trx_avance] (campos opciones_canjeadas, fecha_modificacion y usuario_modificacion), y UPDATE en [sch_proyeccion].[trx_opcion_proyectada] (campo asignado = 1).

5

Respuesta y actualización de UI

Front-end

Se muestra mensaje de éxito y se refrescan las opciones en la pantalla del usuario.

6

Pruebas técnicas directas al API Gateway

API Gateway + JMeter

Como toda la ejecución del canje pasa por el API Gateway del API de Canje, las pruebas de concurrencia e idempotencia (Fase 3) se pueden ejecutar directamente contra él con la herramienta JMeter, sin pasar por el API Promociones Web ni el front-end.

Fase 3 · Validación

Casos de prueba positivos y negativos sobre el flujo de canje.

Casos de prueba positivos (CP)

CP-01 · Canje exitoso desde la Card del Home

Happy path
Acción
Confirmar el canje desde la card del Home.
Resultado esperado
El sistema muestra un mensaje de éxito. En la BD se confirman los INSERT en [sch_canje].[trx_canje] y [sch_canje].[trx_opcion_canjeada], el UPDATE en [sch_puntaje].[trx_avance] (campos opciones_canjeadas, fecha_modificacion y usuario_modificacion) y el UPDATE en [sch_proyeccion].[trx_opcion_proyectada] (campo asignado).

CP-02 · Canje exitoso desde el Detalle de Promoción

Happy path
Acción
Confirmar el canje desde la vista expandida de la promoción.
Resultado esperado
Mismo comportamiento exitoso y mismas inserciones/actualizaciones en la base de datos que en CP-01.

Casos de prueba negativos (CN)

CN-01 · Intento de canje con etapa inactiva

Negativo
Precondición
La etapa de la promoción se encuentra inactiva o expirada en la configuración.
Resultado esperado
El usuario visualiza el botón "Canjear" deshabilitado.

CN-02 · Intento de canje sin opciones suficientes

Negativo
Precondición
El usuario intenta canjear con un saldo de opciones menor al requerido.
Resultado esperado
El sistema muestra el botón "Canjear" deshabilitado.

CN-03 · Falla por falta de configuración de opción

Negativo
Precondición
La opción a canjear no se encuentra parametrizada en la base de datos.
Resultado esperado
La transacción es denegada inmediatamente, sin dejar registros en el esquema de canje.

Pruebas de concurrencia y reintentos

Al tener el API de Canje su propio API Gateway, se puede invocar directamente con JMeter para probar los controles de Redis de forma aislada, sin pasar por el front-end.

CP-03 · Concurrencia — doble petición simultánea

Happy path
Acción
Con JMeter, enviar dos peticiones de canje simultáneas para el mismo invitado/opción directamente al API Gateway del API de Canje.
Resultado esperado
El control de concurrencia en Redis (llave fija) permite que solo una petición se procese; la segunda es rechazada o queda en espera, sin duplicar el INSERT en [sch_canje].[trx_canje] ni el UPDATE en [sch_puntaje].[trx_avance].

CP-04 · Reintentos — idempotencia

Happy path
Acción
Con JMeter, reenviar varias veces seguidas la misma petición de canje (mismo payload) directamente al API Gateway del API de Canje, simulando un reintento del usuario.
Resultado esperado
El control de idempotencia en Redis detecta el reintento y evita procesarlo de nuevo; no se generan registros duplicados en [sch_canje].[trx_canje] ni en [sch_canje].[trx_opcion_canjeada].

CN-04 · Concurrencia — segunda petición debe ser rechazada

Negativo
Precondición
Ya existe una petición de canje en curso para el mismo invitado/opción (llave de concurrencia activa en Redis).
Resultado esperado
La segunda petición simultánea es rechazada de forma controlada por el API de Canje (respuesta de error/bloqueo explícita, no un timeout ni una respuesta genérica), sin duplicar el canje ni dejar inconsistencias en BD.

CN-05 · Idempotencia — reintento no debe reprocesar el canje

Negativo
Precondición
El usuario reintenta la misma petición de canje que ya fue procesada exitosamente.
Resultado esperado
El sistema detecta la idempotencia y no reprocesa la transacción; responde de forma controlada (sin generar un segundo canje ni un error genérico) en lugar de repetir el INSERT/UPDATE en BD.
