Etapa 1 · Preparación

Para poder iniciar las pruebas, el entorno y los datos deben cumplir estrictamente con las siguientes condiciones.

Definition of Ready (DoR)

Accesos y permisos

Este flujo introduce accesos que no estaban en los flujos anteriores. Se diferencian por ambiente/cuenta: DEV en la cuenta Developer de Virginia, QA en la cuenta Developer de Ohio; la BD en la cuenta BD de cada región.

Ambiente DEV · Virginia (cuenta Developer)
  • Front del notario digital: acceso operativo con un usuario que tenga los permisos necesarios para ejecutar sorteos.
  • Componentes cloud del notario digital: permisos para desplegarlos y validarlos, con la estructura de desacoplamiento.
  • BD de resultados (cuenta BD Virginia): acceso a bd_promocion_resultado para validar los ganadores guardados por el proceso.
Ambiente QA · Ohio (cuenta Developer)
  • Front del notario digital: acceso operativo con un usuario que tenga los permisos necesarios para ejecutar sorteos.
  • Componentes cloud del notario digital: permisos para desplegarlos y validarlos, con la estructura de desacoplamiento.
  • BD de resultados (cuenta BD Ohio): acceso a bd_promocion_resultado para validar los ganadores guardados por el proceso.

Pendiente confirmar con Plataforma el detalle de los servicios cloud del notario digital para precisar sus permisos.

Reglas de negocio
  • Vigencia de la etapa: la etapa del sorteo a ejecutar debe encontrarse dentro de la fecha vigente y su estado en el sistema debe ser activo (estado_etapa = 1).
Configuración de datos de prueba
  • Configuración de la mecánica: la base de datos de ejecución debe contar con la configuración previa para el tipo de evento a realizar (Sorteo, Lotería o Lotería Final).
  • Integridad de tablas base: deben estar correctamente parametrizadas y con datos consistentes las siguientes tablas:
    • [sch_configuracion].[cfg_opcion]
    • [sch_proyeccion].[trx_proyeccion]
    • [sch_proyeccion].[cfg_proyeccion_etapa]
    • [sch_proyeccion].[trx_opcion_proyectada]
  • Data de participantes: es obligatorio contar con un volumen de prueba de opciones ya canjeadas y debidamente asignadas a los usuarios participantes.

Etapa 2 · Ejecución

Una vez validadas las precondiciones, se realiza el siguiente flujo operativo en el sistema.

1

Despliegue de componentes cloud

Cloud · Notario Digital

Desplegar los componentes cloud del notario digital con la estructura de desacoplamiento.

2

Configuración del evento

Front del Notario Digital

Ingresar al front del notario digital y generar/confirmar la configuración exacta del evento (sorteo, lotería o lotería final) según los parámetros de la campaña.

3

Generación del sorteo

Front del Notario Digital

Generar el sorteo para la selección de ganadores (sorteo) o la asignación de bolillas ganadoras (lotería).

4

Confirmación y guardado de ganadores

Proceso interno + BD

Confirmar la operación para desencadenar el proceso interno que guarda los ganadores resultantes en la base de datos de destino (bd_promocion_resultado).

Etapa 3 · Validación

Casos de prueba positivos y negativos del proceso de selección y guardado de ganadores.

Casos positivos (escenarios ideales)

CP-01 · Generación exitosa de configuración

Happy path
Condición
La etapa se encuentra dentro de la fecha vigente y el estado_etapa es igual a 1.
Resultado esperado
Desde el front del notario digital se puede generar correctamente la configuración del sorteo o lotería.

CP-02 · Asignación exacta de ganadores

Happy path
Resultado esperado
El sistema asigna correctamente a los ganadores basándose en las opciones canjeadas y asignadas, respetando el límite máximo de cupos o ganadores definidos en la tabla cfg_proyeccion_etapa.

CP-03 · Guardado exitoso en base de datos

Happy path
Resultado esperado
Los datos completos de los ganadores asignados se insertan correctamente en la base de datos bd_promocion_resultado, sin truncamiento, alteración ni pérdida de información.

CP-04 · Trazabilidad de opciones proyectadas

Happy path
Condición
Los ganadores fueron generados y confirmados.
Resultado esperado
Las tablas dependientes (trx_proyeccion y trx_opcion_proyectada) actualizan sus estados correctamente para reflejar que el sorteo ya fue ejecutado y cerrado.

CP-05 · Lectura correcta de opciones válidas

Happy path
Resultado esperado
El proceso de asignación de ganadores toma en cuenta exclusivamente a los usuarios que tengan opciones legítimamente canjeadas y registradas.

Casos negativos (escenarios de error y restricciones)

CN-01 · Ejecución fuera de fecha

Negativo
Condición
La fecha actual del sistema es anterior al inicio o posterior al cierre de la fecha vigente de la etapa.
Resultado esperado
El sistema muestra un mensaje de error restrictivo y bloquea la generación de la configuración.

CN-02 · Estado de etapa inactivo

Negativo
Condición
El campo estado_etapa es diferente de 1 (por ejemplo, 0, 2 o nulo).
Resultado esperado
El sistema no permite iniciar la asignación de ganadores: el botón o acción debe estar deshabilitado o arrojar error.

CN-03 · Ausencia de opciones canjeadas

Negativo
Condición
Se intenta ejecutar la asignación de ganadores cuando la base de datos no registra ninguna opción canjeada.
Resultado esperado
El sistema cancela el proceso.

CN-04 · Fallas de integridad en tablas

Negativo
Condición
Falta información estructural obligatoria en alguna de las tablas base (como configuraciones faltantes en sch_configuracion o sch_proyeccion).
Resultado esperado
El sistema detiene el sorteo y notifica el error.

CN-05 · Fallo en guardado de resultados (rollback)

Negativo
Acción
Simular una pérdida de conexión o un error de permisos al momento de insertar los registros finales en bd_promocion_resultado.
Resultado esperado
El sistema hace un rollback completo de la transacción para evitar que el sorteo quede a medias, y muestra un error en el front.
