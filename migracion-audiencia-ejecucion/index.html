Etapa 1 · Preparación

Asegura que los datos y los estados del sistema estén listos en el servidor de origen antes de que AWS EventBridge inicie el flujo.

Accesos y permisos

Este flujo es 100% AWS y reutiliza en su mayoría los accesos ya otorgados en el flujo de Migración Configuración→Ejecución.

  • Ya cubierto: EventBridge y Fargate ya están otorgados por el flujo anterior — validar que el rol del Fargate tenga permiso sobre el contenedor migracion_audiencia y sobre las dos bases: bd_promocion_audiencia (origen) y bd_promocion_ejecucion (destino).
  • Nuevo: acceso de BD a bd_promocion_audiencia — es una base que no existía en el flujo de Configuración→Ejecución, así que su acceso (lectura para Fargate, y de BD para pruebas) hay que solicitarlo aparte.

Checklist de preparación

  • Disponibilidad de datos: confirmar que la data esté correctamente cargada en la base de datos de origen (bd_promocion_audiencia), específicamente dentro de la tabla [sch_cfg_migracion].[trx_audiencia].
  • Estado de la promoción: validar que el motor de configuración se haya ejecutado previamente. Los registros o la promoción deben contar obligatoriamente con la etapa PRE-EJECUCION.
  • Criterio de fecha: comprobar que la fecha asociada a la pre-ejecución sea una "fecha apta" (actual y válida dentro de la vigencia) para permitir la migración de la audiencia.

Etapa 2 · Ejecución

Se enfoca estrictamente en el flujo de orquestación y procesamiento de AWS.

1

Disparo

AWS EventBridge

Validar que Amazon EventBridge lance el evento programado para las 11:00 PM.

2

Procesamiento

AWS Fargate

Confirmar que el evento inicie exitosamente la tarea de contenedor AWS Fargate migracion_audiencia.

3

Extracción y carga

AWS Fargate

Validar que el Fargate ejecute la acción de EXTRAE sobre bd_promocion_audiencia y, tras procesar, ejecute la acción de CARGA apuntando a la base de datos de destino bd_promocion_ejecucion.

Etapa 3 · Validación

Se revisan los resultados de la migración consultando directamente el motor de base de datos destino (bd_promocion_ejecucion), enfocándose en las tablas transaccionales solicitadas.

Casos de prueba

CP 01 · Carga exitosa en tablas destino

Happy path
Acción / Query
Consultar las tablas trx_audiencia y trx_participante en bd_promocion_ejecucion.
Resultado esperado
Todos los registros que tenían la etapa PRE-EJECUCION y fecha apta se hayan insertado correctamente en ambas tablas tras finalizar la ejecución del Fargate.

CP 02 · Integridad relacional

Happy path
Acción / Query
Comparar los registros insertados en trx_audiencia y trx_participante contra el origen.
Resultado esperado
Sin pérdida de datos, y los atributos de cada participante se hayan mapeado según la regla de negocio.

CP 01 · Falta de conexión Fargate a BD Audiencia

Negativo
Acción / Query
Simular un bloqueo de red o credenciales inválidas entre el contenedor AWS Fargate migracion_audiencia y la base de datos de origen (bd_promocion_audiencia). Detonar el evento.
Resultado esperado
El proceso falla de manera controlada sin afectar el destino, y el error de conexión al origen queda registrado en los logs de CloudWatch.

CP 02 · Falta de conexión Fargate a BD Ejecución

Negativo
Acción / Query
Simular una caída temporal o restricción de red hacia la base de datos de destino (bd_promocion_ejecucion). Detonar el evento.
Resultado esperado
Aunque Fargate logre extraer la data del origen, aborta la operación en la fase de carga (CARGA) de forma segura, reportando el fallo de conexión a destino en los logs.

CP 03 · Etapa inactiva y fuera de horario

Negativo
Acción / Query
Al momento de intentar realizar la carga, configurar la promoción en el origen para que la etapa PRE-EJECUCION ya no se encuentre activa y su horario no sea el apto.
Resultado esperado
En la BD Ejecución los registros no se insertan en las tablas trx_audiencia ni trx_participante, confirmando que el proceso verifica y respeta estas condiciones en el momento exacto de la carga.
